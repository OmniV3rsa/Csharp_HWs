Задача 1.1

1. ProcessDamage принимает List<IDamageable>, чтобы в один список можно было класть разные объекты вроде Player и Trap. Иначе пришлось бы делать отдельные методы для каждого класса. За счет полиморфизма GameSystem просто вызывает TakeDamage у всех подряд, а каждый класс сам решает, что делать.

2. Формально контракт интерфейса не нарушен, потому что у Trap есть и HP, и TakeDamage. Но по логике для вызывающего кода это странно. Обычно ждут, что после урона HP уменьшится, а тут HP всегда 10 и сеттер пустой, хотя метод возвращает false как будто ловушка сломалась.

3. Если попытаться передать HealthPotion в ProcessDamage, код просто не скомпилируется из-за ошибки типов, так как у зелья нет интерфейса IDamageable. Если бы ему специально прикрутили IDamageable и лечили отрицательным уроном, пришлось бы придумывать ему лишнее HP. Тогда при обычной атаке по всем целям можно было бы случайно "ударить" зелье и словить баги.

4. Придется менять Player и Trap, потому что оба реализуют IDamageable. Если не добавить им IsDead, программа просто не скомпилируется с ошибкой. Это и есть нарушение принципа контракта - раз класс подписался на интерфейс, он обязан реализовать все его свойства и методы.

Задача 1.2

| Утверждение | Abstract class | Interface |
|---|---|---|
| Может содержать поля с конкретными значениями | + | - |
| Может иметь полноценный конструктор | + | - |
| Один класс может наследовать/реализовывать несколько таких типов | - | + |
| Может содержать реализацию метода по умолчанию | + | + |
| Может объявлять свойства без реализации | + | + |
| Может быть использован как тип поля или переменной | + | + |
| Может наследовать классы | + | - |
| Может содержать приватные методы | + | + |

1. В абстрактном классе можно хранить обычные поля, а в интерфейсе нет.
2. У абстрактного класса бывает конструктор, у интерфейса конструктора нет.
3. Наследоваться можно только от одного класса, а интерфейсов можно навесить сколько угодно.
4. Обычные методы есть в абстрактном классе, а в интерфейсе реализации по умолчанию разрешили с C# 8.
5. В абстрактном классе можно сделать abstract свойство, а в интерфейсе они и так без реализации.
6. Оба можно указывать как тип переменной или поля, чтобы класть туда наследников.
7. Абстрактный класс может наследоваться от другого класса, а интерфейс только от интерфейсов.
8. Приватные методы есть в абстрактном классе, и в интерфейсах их тоже добавили начиная с C# 8.

Доп вопрос

abstract class Character (HP, TakeDamage)
- Player : Character, IInteractable, IHealable
- NPC : Character, IInteractable
- Enemy : Character

Все трое являются персонажами и могут получать урон, поэтому общие поля и метод урона выносим в абстрактный класс Character, чтобы не дублировать код. Абстрактный класс нужен, когда есть связь "является" и общее состояние. А интерфейсы нужны для отдельных способностей ("умеет делать") - диалоги выносим в IInteractable для Player и NPC, а хил в IHealable только для Player.
